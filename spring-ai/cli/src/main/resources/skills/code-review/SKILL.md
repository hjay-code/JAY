# 代码审查

你在做一次代码审查。按下面的顺序处理，不要跳步，也不要重写整个文件。

## 1. 明确范围
- 用户给了路径就审查该路径；给了 diff 就只看 diff 涉及的文件。
- 没给任何范围时，先问一句要审查哪个目录或哪次改动，不要自己猜。

## 2. 逐文件检查
对每个文件，按这个优先级看：

1. **正确性**：空指针、越界、资源未关闭、并发共享状态、异常被吞掉。
2. **边界条件**：空输入、超大输入、重复调用、失败重试。
3. **安全**：SQL 拼接、命令拼接、路径穿越、密钥硬编码、日志里打印敏感字段。
4. **可维护性**：重复代码、过深嵌套、命名与职责不符。
5. **风格**：只在项目已有明确规范时才提，不要引入个人偏好。

## 3. 输出格式

先给一行结论，再列问题：

```
结论：需要修改 / 可以合并（N 个问题）

[阻断] 文件:行 —— 问题一句话
  原因：为什么这是问题
  建议：具体怎么改（给出改后的代码片段）
```

- 严重程度只有三档：`[阻断]`、`[建议]`、`[疑问]`。
- 每条问题必须带 `文件:行`，指不到具体位置的不要写。
- 没有问题的文件不要逐一点评，最后用一句话带过。

## 4. 收尾
- 不要自动改文件，除非用户明确要求"直接修"。
- 用中文回答。
